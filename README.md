# Mini-pretrain LLM на русском корпусе Wikipedia

## Описание проекта

В рамках работы был реализован и протестирован полный пайплайн **mini-pretrain языковой модели с нуля** на русскоязычном корпусе Wikipedia.  

В рамках проекта были выполнены:

- загрузка и подготовка датасета;
- токенизация текстов;
- сохранение токенизированного корпуса в `parquet`-шарды;
- повторная загрузка шардов и фиксированный `train/eval split`;
- обучение модели в режиме causal language modeling;
- серия smoke-тестов на Kaggle;
- финальные 30-минутные запуски на A100;
- сравнение конфигураций по `eval_loss`;
- генерация текстов лучшей моделью.

## Использованные данные и модель

- **Датасет:** `wikimedia/wikipedia`, подмножество `20231101.ru`
- **Токенизатор:** `ai-forever/rugpt3small_based_on_gpt2`
- **Тип задачи:** causal language modeling
- **Модель:** `Qwen3ForCausalLM`, инициализированная с нуля через `Qwen3Config`
- **Размер модели:** около **0.96B параметров**

В ходе работы был реализован следующий пайплайн:

1. загрузка исходного датасета;
2. токенизация текстов;
3. сохранение токенизированного корпуса в `parquet`-шарды;
4. повторная загрузка шардов;
5. фиксированный `train/eval split`;
6. обучение модели с ограничением по времени;
7. логирование метрик и расчет `eval_loss`;
8. генерация текстов по пользовательским prompt'ам.

## Этап 1. Smoke-тесты на Kaggle (2×T4)

Этап Kaggle использовался как **техническая отладка пайплайна** перед финальным запуском на A100.  
Основная цель этого этапа состояла не в достижении лучшего качества, а в проверке, что:

- обучение стартует и завершается без ошибок;
- корректно работают `Trainer`, evaluation и checkpointing;
- не возникает проблем с памятью и диском;
- выбранные гиперпараметры ведут себя предсказуемо на коротких прогонах.

### Стабильный базовый smoke-run

На первом этапе был успешно выполнен минимальный smoke-test со следующей конфигурацией:

- `per_device_train_batch_size = 2`
- `train_dataset = train_dataset.select(range(128))`
- `eval_dataset = eval_dataset.select(range(16))`

На ранних попытках основные проблемы были связаны не с логикой обучения, а с окружением:

- возникал `CUDA OOM` в неочищенной сессии;
- сохранение checkpoint'ов приводило к runtime error;
- директория `/kaggle/working/output_dir/gpt2-1b-russian` разрасталась и заполняла диск.

Для стабилизации smoke-run были внесены временные изменения:

- `save_steps = 100`
- `load_best_model_at_end = False`
- перед повторным запуском удалялась старая директория checkpoint'ов:
  - `/kaggle/working/output_dir/gpt2-1b-russian`

**Результат:** запуск завершился без ошибок, итоговый `eval_loss = 11.1493`.

### Расширенный smoke-run

После первичной отладки был выполнен более содержательный запуск:

- `train_dataset = train_dataset.select(range(512))`
- `eval_dataset = eval_dataset.select(range(64))`
- `per_device_train_batch_size = 4`
- `gradient_accumulation_steps = 1`

Для этого прогона число шагов обучения составляло примерно:

`steps_per_epoch ≈ len(train_dataset) / (per_device_train_batch_size * num_gpus * gradient_accumulation_steps)`

При `2 GPU` это давало около `64` шагов на эпоху.

Перед запуском также очищалась директория со старыми checkpoint'ами:

**Результат:** обучение и финальная evaluation завершились успешно, итоговый `eval_loss = 10.8394`.

Именно конфигурация `train=512`, `eval=64` была выбрана как основной Kaggle smoke-baseline для последующих технических сравнений.

### Краткие сравнения гиперпараметров на Kaggle

На базе конфигурации `512 / 64` были проведены короткие sanity-check эксперименты.

| Проверка | Конфигурации | Результат | Вывод |
|---|---|---:|---|
| `gradient_accumulation_steps` | `1` vs `2` | `10.8394` vs `11.1141` | Для smoke-run лучше оказался `gradient_accumulation_steps = 1` |
| `torch_compile` | `True` vs `False` | `10.8394` vs `10.7838` | В Kaggle выгоднее оказался `torch_compile = False` |
| `warmup_steps` | `200` vs `0` | `10.7838` / `10.8394` vs `8.7197` | Для коротких прогонов большой warmup был невыгоден |
| `learning_rate` | `5e-5` vs `2e-5` | `8.7197` vs `10.4014` | `2e-5` оказался слишком медленным |
| `lr_scheduler_type` | `linear` vs `constant` | `9.1482` vs `8.6907` | На коротком прогоне лучше сработал `constant` |

### Итог по этапу Kaggle

По результатам smoke-тестов были сделаны следующие промежуточные выводы:

- пайплайн обучения, evaluation и сохранения данных работает корректно;
- для коротких отладочных прогонов длинный warmup неэффективен;
- `learning_rate = 5e-5` оказался разумной базовой точкой для smoke-run;
- `torch_compile = False` в данном окружении был быстрее и стабильнее;
- для коротких Kaggle-проверок `lr_scheduler_type = "constant"` показал себя лучше, чем `linear`.

Важно, что эти выводы относились **только к коротким debug/smoke-прогонам на Kaggle** и использовались как ориентир при подготовке финальных запусков на более мощной GPU.

## Оценка стартовых значений effective batch size и learning rate

Перед подготовкой кандидатов для запуска на A100 начальные значения effective batch size и learning rate оценивались по формулам:

\[
\eta(N, D) = 1.79 N^{-0.713} D^{0.307}
\]

\[
B(D) = 0.58 D^{0.571}
\]

где:

- \(N \approx 10^9\) — размер модели;
- \(D = M \cdot L\) — число токенов в train-корпусе;
- \(M = 1{,}940{,}063\) — число объектов в train;
- \(L = 512\) — длина одного объекта после токенизации и padding.

Отсюда:

\[
D = 1{,}940{,}063 \cdot 512 = 993{,}312{,}256 \approx 10^9
\]

Оценки дали:

- **effective batch size:** около **80 000 токенов**
- **effective batch size в объектах:** около **156**, то есть ориентир **150–160 объектов**
- **learning rate:** около **`4e-4`**

Эти значения использовались как стартовая эвристика при подготовке кандидатных конфигураций для A100.

## Предварительный shortlist конфигов перед финальным запуском

После серии Kaggle smoke-тестов был подготовлен shortlist кандидатов для финального запуска на **1×A100**.

В качестве рабочей основы переносились следующие решения:

- `optim = "adamw_torch"`
- `torch_compile = False`
- `learning_rate = 5e-5` как надежный базовый кандидат
- `lr_scheduler_type = "constant"` как рабочий вариант для коротких прогонов

При выборе batch size учитывалось, что важен не только `per_device_train_batch_size`, а **effective batch size**:

`effective_batch = per_device_train_batch_size * num_gpus * gradient_accumulation_steps`

Так как финальный запуск выполнялся на одной GPU, effective batch size достигался комбинацией `per_device_train_batch_size` и `gradient_accumulation_steps`.

## Этап 2. Финальные эксперименты на A100 SXM 80GB

После отладки на Kaggle эксперименты были перенесены на удалённую машину с **GPU A100 SXM 80GB**, где выполнялись финальные 30-минутные прогоны.

### Общая конфигурация финальных запусков

Во всех финальных экспериментах использовались:

- `optim = "adamw_torch"`
- `num_train_epochs = 1`
- `per_device_train_batch_size = 8`
- `save_steps = 1000`
- `save_total_limit = 1`
- `weight_decay = 0.01`
- `logging_steps = 10`
- `eval_steps = 1000`
- `eval_strategy = "steps"`
- `load_best_model_at_end = True`
- `metric_for_best_model = "eval_loss"`
- `gradient_checkpointing = False`
- `dataloader_num_workers = 4`
- `torch_compile = False`
- `bf16 = True`
- `lr_scheduler_type = "linear"`

Менялись три ключевых параметра:

- `learning_rate`
- `warmup_steps`
- `gradient_accumulation_steps`

### Протестированные конфигурации

#### Эксперимент 1 — базовый осторожный запуск

- `learning_rate = 5e-5`
- `warmup_steps = 200`
- `gradient_accumulation_steps = 20`

Это была базовая точка сравнения, наиболее близкая к осторожной настройке, с которой удобно сравнивать более агрессивные варианты. По результатам этого эксперимента было принято решение отказаться от тестирования конфигураций A100_CANDIDATE_2 и A100_CANDIDATE_3 и перейти к более аггресивным настройкам.

#### Эксперимент 2 — агрессивный запуск с большим lr и без warmup

- `learning_rate = 4e-4`
- `warmup_steps = 0`
- `gradient_accumulation_steps = 20`

Здесь проверялась гипотеза, что для короткого 30-минутного прогона длинный warmup не позволяет эффективно использовать доступное окно обучения.

#### Эксперимент 3 — агрессивный запуск без warmup и с меньшим effective batch size

- `learning_rate = 4e-4`
- `warmup_steps = 0`
- `gradient_accumulation_steps = 10`

В этом эксперименте дополнительно уменьшался effective batch size, чтобы за те же 30 минут модель успела сделать больше обновлений весов.

### Результаты финальных запусков

| Эксперимент | Название конфигурации | `learning_rate` | `warmup_steps` | `gradient_accumulation_steps` | `eval_loss` |
|---|---|---:|---:|---:|---:|
| 1 | `A100_CANDIDATE_1` | `5e-5` | `200` | `20` | `7.3301` |
| 2 | `A100_CANDIDATE_4` | `4e-4` | `0` | `20` | `5.4760` |
| 3 | `A100_CANDIDATE_5` | `4e-4` | `0` | `10` | **5.2778** |

### Лучший результат

Лучший результат показал **Эксперимент 3**:

- `learning_rate = 4e-4`
- `warmup_steps = 0`
- `gradient_accumulation_steps = 10`
- `eval_loss = 5.2778`

Если сравнить его с базовой конфигурацией, снижение `eval_loss` составило примерно **28%**.  
По сравнению с Экспериментом 2 дополнительное улучшение составило около **3.6%**.

## Наблюдения и выводы

### 1. Kaggle-этап выполнил свою задачу как этап технической стабилизации

Эксперименты на Kaggle позволили:

- отладить полный пайплайн обучения;
- устранить проблемы с памятью, checkpoint'ами и переполнением диска;
- проверить работоспособность токенизации, загрузки шардов, training loop и evaluation;
- провести быстрые sanity-check сравнения ключевых гиперпараметров.

Именно этот этап позволил перейти к финальным экспериментам на A100 уже с рабочей и устойчивой инфраструктурой.

### 2. Длинный warmup оказался неэффективным в коротком pretrain-окне

Этот вывод появился уже на Kaggle и подтвердился на A100.  
На коротких прогонах длинный warmup приводит к тому, что значительная часть доступного времени тратится на обучение с заниженным learning rate.

В финальной серии запусков конфигурация с:

- `learning_rate = 5e-5`
- `warmup_steps = 200`

показала худший результат (`eval_loss = 7.3301`).

### 3. Более агрессивный learning rate оказался полезнее осторожной настройки

На Kaggle это сначала проявилось как sanity-check: `5e-5` заметно лучше отработал, чем `2e-5`, то есть слишком маленький шаг обучения был слишком медленным даже для коротких прогонов.

На A100 эта логика получила дальнейшее развитие: переход к

- `learning_rate = 4e-4`
- `warmup_steps = 0`

дал резкое улучшение качества по сравнению с осторожной базовой конфигурацией.

Это показывает, что для короткого mini-pretrain с нуля модель выигрывает от более агрессивной оптимизации, если обучение при этом остается стабильным.

### 4. Более частые обновления весов оказались выгоднее большого effective batch size

В финальной серии экспериментов при фиксированном `learning_rate = 4e-4` уменьшение

- `gradient_accumulation_steps: 20 -> 10`

дало лучший итоговый `eval_loss`.

Наиболее вероятное объяснение состоит в том, что при фиксированном лимите по времени модель успевала сделать больше optimizer steps, а значит — больше полезных обновлений параметров.

### 5. Обучение оставалось стабильным даже в агрессивном режиме

Несмотря на довольно агрессивную конфигурацию:

- `learning_rate = 4e-4`
- `warmup_steps = 0`

по логам не наблюдалось явного развала обучения. Loss снижался устойчиво, без очевидных признаков нестабильности, что делает такую настройку практически оправданной именно для данного ограниченного режима pretrain.

### 6. Короткий pretrain уже позволяет модели усвоить структуру корпуса

Примеры генерации показывают, что модель начала воспроизводить:

- энциклопедическую форму текста;
- заголовки и подзаголовки;
- псевдо-справочные перечисления;
- характерную ритмику русскоязычных описательных фрагментов.

Однако смысловая связность, фактическая точность и общая когерентность пока остаются низкими. Для короткого запуска с нуля это ожидаемый результат.

## Итог

В рамках работы был реализован полный mini-pretrain pipeline для языковой модели на русском корпусе Wikipedia и проведена серия экспериментов в два этапа:

1. **Kaggle (2×T4)** — техническая отладка и быстрые smoke-тесты;
2. **A100 SXM 80GB** — финальные 30-минутные запуски и сравнение гиперпараметров.

Лучший результат показала конфигурация candidate5:

- `per_device_train_batch_size = 8`
- `gradient_accumulation_steps = 10`
- `learning_rate = 4e-4`
- `warmup_steps = 0`
- `lr_scheduler_type = "linear"`

Итоговое значение:

- **`eval_loss = 5.2778`**

Проведенные эксперименты показали, что для короткого mini-pretrain запуска длиной 30 минут:

- слишком осторожная настройка с большим warmup неэффективна;
- более агрессивный learning rate может работать лучше;
- уменьшение effective batch size помогает за то же время сделать больше полезных обновлений;
- даже короткое обучение с нуля позволяет модели начать воспроизводить структуру целевого корпуса.
